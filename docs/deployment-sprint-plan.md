# MIRA: Kubernetes deployment sprint plan

Written for: the MIRA dev team and whoever operates the cluster.

Scope: make the SvelteKit/adapter-node app safely deployable on a k8s cluster, with Postgres external (managed or operator-run) and PLANTdataHUB (GitLab) as OIDC provider.

Based on a repo audit at commit `542e8db`. I ran `pnpm build` to verify finding B1 below.

---

## 1. Audit findings

Severity: **B** = blocks deployment (it breaks or leaks on day one). **H** = fix before real users. **M** = fix soon after.

[drizzle.config.ts](../drizzle.config.ts) needs `process.env.DATABASE_URL`. The runtime image does not need dev deps.                      | A fresh cluster has an empty database and the app errors on first query. | B6  | **There are no health or readiness endpoints.**                                     | No `/healthz` or `/readyz` route.                                                                                                                                                                                                                      | k8s cannot tell a stuck pod from a good one. The only option is probing `/`, which runs a DB-backed session lookup and the dashboard queries.                                                                                                                                      |

| --- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| H1  | **Open self-registration is enabled alongside OIDC.**                                | `emailAndPassword: { enabled: true }` in [auth.ts](../src/lib/server/auth.ts).                                                                                                                                                      | Anyone who can reach the host can create an account. Every `locals.user` check in the app then passes: BrAPI, the dashboard, the RO-Crate download. Nothing else in the app grants access: a signed-in user is a trusted user. If OIDC-only is the intent, disable it.            |

| H3  | **OAuth tokens are stored in the database in plaintext.**                            | The better-auth `account` table holds the GitLab `accessToken`/`refreshToken`. The config does not enable token encryption (check the option for the pinned version, `account.encryptOAuthTokens`).                                 | A DB backup or read-only SQL access gives write-scope (`api`) tokens for PLANTdataHUB. The `api` scope in [.env.example](../.env.example) is much broader than the `read_api` its own comment says is needed.                                                                     |
| H4  | **The BrAPI endpoints are cookie-session only.**                                     | Every `/[repo]/brapi/v2/**` handler starts with `if (!event.locals.user) error(401)`.                                                                                                                                               | The point of a BrAPI server is that clients (BMS, Breedbase tools, scripts) can call it. They have no browser session. This is a product decision to make before deployment. The options are: public read, API tokens, or OIDC bearer validation. Sprint 2 time-boxes a spike.    |
| H5  | **The ETL runs inside the HTTP request.**                                            | [pipeline.ts](../src/lib/server/etl/pipeline.ts) and `arcs/[id]/+page.server.ts` run Extract, Transform and Load in one form action. The `fetch` calls to GitLab in [extract.ts](../src/lib/server/etl/extract.ts) have no timeout. | Large ARCs run past ingress timeouts (nginx default is 60s) or a rolling restart kills them mid-load. Load is transactional, so the data is safe, but the status row is left stale. There is also no concurrency guard: two users, or two replicas, can run the same ARC at once. |
| H6  | **Replicas share nothing, and some state is in memory.**                             | Request-log queue ([request-logs.ts](../src/lib/server/db/request-logs.ts)), better-auth's default in-memory rate limiter, and the NCBI cache in transform.ts.                                                                      | The log queue loses up to 500ms of data on `SIGTERM`, and there is no shutdown hook. Rate limits are per pod. The NCBI cache is harmless but cold on every pod.                                                                                                                   |
| H7  | **The DB client uses defaults.**                                                     | `postgres(env.DATABASE_URL)` in [db/index.ts](../src/lib/server/db/index.ts). There is no `max`, no `idle_timeout`, no `connect_timeout`, no TLS option, and no `SIGTERM` `end()`.                                                  | With N replicas the app uses N×10 connections, which can exhaust a managed Postgres or PgBouncer. It cannot require TLS to the DB. Shutdown leaves connections open.                                                                                                              |
| H8  | **The ETL makes outbound calls that need egress rules.**                             | PLANTdataHUB (the host in `OIDC_ISSUER_URL`) and NCBI E-utils (`eutils.ncbi.nlm.nih.gov`, from transform.ts).                                                                                                                       | A default-deny NetworkPolicy breaks login and import. NCBI failure is already best-effort (returns `undefined`), so it only degrades one column.                                                                                                                                  |
| H9  | **The ETL write path has no per-user authorization.**                                | Any signed-in user can Extract and Load any ARC their GitLab token can read, and it overwrites the shared BrAPI tables.                                                                                                             | With H1 closed, only PLANTdataHUB users can do this. Still decide whether import should be restricted to maintainers or admins.                                                                                                                                                   |

### Medium

| #   | Finding                                                                                                                                                                                                                                               | Evidence |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| M1  | **There are no tests.** `git ls-files` has no `*.test.ts`. CI (once it exists) would be a build-only gate. The pipeline (transform and load) is the highest-risk code.                                                                                |
| M2  | **`request_logs` grows without bound.** It has no retention or partitioning. It stores the raw `pathname`, so cardinality depends on `[repo]` and ID segments (the unmatched-endpoint concern). It is also written for 404s on random scanned paths.  |
| M3  | **The local-dev Postgres setup is unsafe if copied.** `compose.yaml` uses an unpinned `postgres` tag, a weak hardcoded password, and port 5432 published on all interfaces. The `.env.example` default `DATABASE_URL` matches it.                     |
| M4  | **Dev tooling is in the install path.** Playwright, `@better-auth/cli` and `auth` are in `devDependencies`. A naive `pnpm install` in the image pulls them. `engine-strict=true` in `.npmrc` has no `engines` field. Node 22 is used locally. Pin it. |
| M5  | **There is no structured logging.** Only `console.error` in request-logs. There is no request ID, no log level, and no metrics endpoint. The dashboard is the only observability, and it lives in the same DB.                                        |
| M6  | **`robots.txt` allows all crawling**, including `/[repo]/brapi/...` and `/arcs`.                                                                                                                                                                      |
| M7  | **There are no security headers** (CSP, HSTS, `X-Content-Type-Options`). SvelteKit's `csrf.checkOrigin` is on by default, which is good.                                                                                                              |
| M8  | **`saveLayout` JSON is only checked to be an array.** It is stored as `jsonb` with no per-item validation or size limit.                                                                                                                              |
| M9  | **The README is the unmodified `sv create` template.** It has no deployment, env var or operations docs.                                                                                                                                              |

### Checked and fine

- No hard-coded `localhost`, no file writes, and no temp files in `src/`. Config uses `$env/dynamic/private`, which is read at runtime, so one image works across environments. The build succeeds without env vars.
- `.env` is untracked and gitignored. `.env.example` has no real secrets.
- The auth tables have indexes, the `request_logs` tables have indexes, and BrAPI tables are arc-scoped with unique `(arc_id, source_id)` keys.
- Load runs in one transaction, so a failed import leaves no partial data.
- The OIDC setup is provider-agnostic via discovery and uses PKCE. The client secret is optional, so it supports a public client.

**Env vars as implemented in session A** (validated at boot by `src/lib/server/env.ts`; full docs in `.env.example`):

| Variable             | Required | Notes                                                                                                     |
| -------------------- | -------- | --------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`       | yes      | `postgres://` or `postgresql://` URL                                                                      |
| `ORIGIN`             | yes      | scheme + host (+ port), no path or trailing slash; `https` unless `NODE_ENV` is `development`/`test`      |
| `BETTER_AUTH_SECRET` | yes      | at least 32 chars                                                                                         |
| `OIDC_ISSUER_URL`    | yes      | no trailing slash, no `/.well-known` suffix                                                               |
| `OIDC_CLIENT_ID`     | yes      |                                                                                                           |
| `OIDC_CLIENT_SECRET` | no       | empty = public client                                                                                     |
| `OIDC_SCOPES`        | no       | space separated, default `openid profile email`                                                           |
| `ADMIN_EMAILS`       | no       | comma separated e-mails made admin at sign-in, everyone else is a user (S2.2); chart `config.adminEmails` |
| `DB_POOL_MAX`        | no       | default 10 per process                                                                                    |
| `DB_IDLE_TIMEOUT`    | no       | seconds, default never                                                                                    |
| `DB_CONNECT_TIMEOUT` | no       | seconds, default 30                                                                                       |
| `DB_SSL`             | no       | `true`/`require`/`allow`/`prefer`/`verify-full`; unset or `false` = off                                   |
| `DB_PREPARE`         | no       | `true` (default) or `false`; only for a PgBouncer older than 1.21 (session E)                             |

Also read by adapter-node (not validated by MIRA): `PORT`, `HOST`, `PROTOCOL_HEADER`, `HOST_HEADER`, `ADDRESS_HEADER`, `XFF_DEPTH`, `SHUTDOWN_TIMEOUT` (seconds, default 30). Set `terminationGracePeriodSeconds` above `SHUTDOWN_TIMEOUT` plus a few seconds for the log flush and pool close.

**Probes:** `GET /healthz` (liveness, no DB), `GET /readyz` (readiness, `select 1`, 2s timeout, 503 on failure). Neither needs cookies and neither is logged.

**Shutdown:** adapter-node traps SIGTERM/SIGINT, drains in-flight requests, then emits `sveltekit:shutdown`; the app flushes request logs (3s bound) and ends the DB pool (5s bound) there, and the process exits on its own.

**Packaging as implemented in session B** (details in [docker.md](docker.md) and [migrations.md](migrations.md)):

- **Image:** `<registry>/<owner>/mira`, built by `.github/workflows/ci.yml` and pushed to GHCR (`ghcr.io/<owner>/mira`) only on `main`, tagged with the full commit SHA (`mira:<40-hex-sha>`). There is no `latest` tag: pin the SHA or digest in the chart. Override the registry with the repo variable `IMAGE_NAME` and the secrets `REGISTRY`, `REGISTRY_USERNAME`, `REGISTRY_PASSWORD`.
- **App container:** default `CMD ["node", "build"]`, working directory `/app`, port 3000, UID/GID 1000 (`runAsNonRoot` works), writes nothing to disk (`readOnlyRootFilesystem: true`, no `/tmp` volume needed).
- **Migration:** same image, `command: ["node", "migrate.js"]`, working directory `/app` (the image default; or set `MIGRATIONS_FOLDER`). Needs only `DATABASE_URL` (optional `DB_SSL`), not `ORIGIN` or the auth secrets. Prints one `migrate: applied <tag>` line per migration; a second run is a no-op; exit 1 on failure. Run as a pre-install/pre-upgrade Job or initContainer, never at app boot.
- **Build facts:** `pnpm build` and `pnpm build:migrate` need no env vars; `pnpm check` is `scripts/check.mjs` (ignores third-party diagnostics in `node_modules`, `check:raw` is the plain command); `pnpm audit --prod --audit-level high` passes thanks to `overrides` in `pnpm-workspace.yaml`.

**Chart as implemented in session C** (details in [deploy/helm/mira/README.md](../deploy/helm/mira/README.md)):

- **Path:** `deploy/helm/mira` (plain Helm, no subcharts, no Postgres). Example values for CI and the README: `deploy/helm/mira/ci/*.yaml`. CI job `chart` runs `helm lint`, `helm template` and `kubeconform -strict` on them.
- **Required values** (no defaults; `values.schema.json` rejects the install otherwise): `image.tag` (40-hex commit SHA), `ingress.host` (or `ingress.enabled=false` plus `config.origin`), `config.oidc.issuerUrl`, `config.oidc.clientId`, `secrets.database.name`, `secrets.authSecret.name`.
- **Secrets** (must pre-exist in the namespace; the chart creates none): `secrets.database` (default key `DATABASE_URL`), `secrets.authSecret` (default key `BETTER_AUTH_SECRET`), optional `secrets.oidcClientSecret` (default key `OIDC_CLIENT_SECRET`, empty name = public client), optional `migration.databaseSecret` (default key `DATABASE_URL`; empty name = reuse `secrets.database`). For a CloudNativePG Secret use key `uri`.
- **Migration:** hook Job `<release>-mira-migrate`, `pre-install,pre-upgrade`, `node migrate.js`. It runs as a pre-existing ServiceAccount (`migration.serviceAccountName`, default `default`) and reads no ConfigMap, because hooks run before chart resources exist. `helm rollback` runs no migration and migrations are forward-only.
- **ORIGIN** is `https://<ingress.host>` unless `config.origin` is set. Verified against the image: with `ORIGIN` set, adapter-node ignores `PROTOCOL_HEADER`/`HOST_HEADER`; they are set only as a safety net. `ADDRESS_HEADER` is unset on purpose (the app never reads the client IP).
- **Redirect URI** to register (also in `NOTES.txt`): `<ORIGIN>/api/auth/oauth2/callback/oidc`.
- **Defaults to review in S1.8:** `config.oidc.scopes` is `openid profile email read_api` (the app's own default has no GitLab API scope).
- **Not verified (needs a cluster):** ingress headers end to end, hook ordering, PDB and rollout behaviour under load. (The CloudNativePG Secret key names were read from the operator source in session E, see below.)

**ETL worker as implemented in session D** (details in [etl-worker.md](etl-worker.md)):

- **Image command:** `node worker.js` (same image, working directory `/app`, no port). Needs the app's env (`DATABASE_URL`, `ORIGIN`, `BETTER_AUTH_SECRET`, `OIDC_*`).
- **New env vars** (validated at boot): `HTTP_HEADERS_TIMEOUT` (30 s), `HTTP_TIMEOUT` (300 s), `ETL_CONCURRENCY` (1), `ETL_LEASE_SECONDS` (60), `ETL_POLL_SECONDS` (5), `ETL_MAX_ATTEMPTS` (3), `ETL_RETRY_DELAY_SECONDS` (30), `ETL_SHUTDOWN_TIMEOUT` (60).
- **Queue:** table `etl_job` (migration `0003_etl_job`, DML only at runtime), `FOR UPDATE SKIP LOCKED`, one active job per ARC (a second Import click is deduplicated), lease + heartbeat, retries only for transient errors, per-ARC `pg_advisory_xact_lock` in Load. No pg-boss.
- **Job states:** `queued` (also while waiting to retry), `running`, `succeeded`, `failed`. The ARC page polls `/arcs/<id>/job` only while a job is active.
- **Token:** the worker runs as the importing user's linked `oidc` account and refreshes through better-auth with a `userId`. Expired or revoked refresh token: the job fails at once with "sign in again and retry".
- **Chart:** `worker.*` values (`enabled`, `replicas`, `concurrency`, `leaseSeconds`, `pollSeconds`, `shutdownTimeoutSeconds`, `resources`, PDB for >1 replica) and shared `config.http.*`, `config.etl.*`. No Service or probes. The ingress `proxy-read-timeout` workaround is gone.
- **CI:** `verify` has a `postgres:17` service and `TEST_DATABASE_URL` for the queue tests; the `chart` job renders five value sets.
- **Not verified:** real GitLab refresh, a real ARC's import time, the rollout on a cluster, PgBouncer. For the exit demo: import a real ARC, restart the web and worker pods during it.

## 3. Decisions and remaining risks

**Decided (answers from the team):**

1. **Visibility:** only users with GitLab access to the ARC. This adds S2.4b and makes S2.2's admin role about operations, not data access.
2. **BrAPI auth:** per-user API tokens (S2.4).
3. **Postgres:** in-cluster CloudNativePG (S1.10, now 3d).
4. **ARC size:** imports can exceed 1 minute, so the background worker moved into Sprint 1 (S1.11). Sprint 1 is now about 20 ideal days for 2 developers, which is tight. If it slips, move S1.9's image scan and S1.10's PgBouncer to Sprint 2 first.

**Remaining risks and open questions:**

1. **Token lifetime vs background work:** GitLab access tokens expire (2h by default). The worker and token-authenticated BrAPI calls both depend on a refresh token that stays valid. Verify refresh on staging with an expired access token. Decide the failure mode (S1.11, S2.4b).
2. **The ARC access check couples BrAPI latency to GitLab availability.** The cache TTL trades freshness against load. Decide the TTL and the behavior when GitLab is down (fail closed is the safe default).
3. **Single issuer:** the code assumes one PLANTdataHUB. Confirm there is no multi-instance requirement.
4. **Data already imported:** BrAPI rows are keyed by `arc_id`, so the access check can use the existing key. Contacts are global (shared) rows and can reveal people across ARCs. Decide whether that is acceptable.

## 4. Definition of done for "safely deployable"

- Image built and scanned by CI, deployed by chart with no manual steps, no secrets in git.
- Migrations run as a Job. Rollback tested.
- Login works via OIDC only. Admin-only dashboard. Tokens encrypted. ARC data is visible only to users with GitLab access. BrAPI clients use API tokens.
- Probes, graceful shutdown and PDB: a rolling update causes no failed requests.
- Backups restore-tested. Alerts exist for readiness, error rate and failed imports.
- A runbook exists in the repo.
